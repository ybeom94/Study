# PART 01. 컴퓨터 구조 (Computer Architecture)

## Chapter01. 컴퓨터 구조 시작하기
<details>
<summary>핵심 개념 펼치기</summary>

### 1. 컴퓨터 구조를 배우는 이유

컴퓨터 구조는 프로그램이 **어떤 하드웨어에서 어떤 순서로 실행되는지**를 이해하는 분야입니다. 같은 프로그램도 CPU의 처리 능력, 메모리 용량, 저장장치 속도에 따라 실행 시간이 달라집니다. 오류가 발생했을 때도 단순히 코드만 보는 것이 아니라 **CPU·메모리·입출력 중 어디가 병목인지** 생각할 수 있게 됩니다.

### 2. 컴퓨터가 이해하는 두 종류의 정보

- **데이터(Data):** 처리 대상이 되는 숫자·문자·이미지 등의 값
- **명령어(Instruction):** CPU에 어떤 연산을 수행할지 알려 주는 정보

예를 들어 `10 + 20`을 계산할 때, `10`과 `20`은 데이터이고 **덧셈을 수행하라**는 지시가 명령어에 해당합니다.

### 3. 컴퓨터의 4가지 핵심 부품

| 구성 요소 | 주된 역할 | 이해할 점 |
|---|---|---|
| **CPU** | 명령어를 해석하고 실행 | 연산과 전체 실행 흐름 제어 |
| **주기억장치(RAM)** | 실행 중인 명령어·데이터 보관 | 빠르지만 일반적으로 휘발성 |
| **보조기억장치** | 파일·프로그램 장기 보관 | 전원이 꺼져도 데이터 유지 |
| **입출력장치** | 외부와 정보 교환 | 키보드·모니터 등 |

CPU 내부의 **ALU**는 계산을 수행하고, **제어장치**는 제어 신호를 만들며, **레지스터**는 당장 필요한 값·주소·명령어를 임시 저장합니다.

### 4. 메인보드와 시스템 버스

부품은 메인보드의 연결 통로를 통해 통신합니다. 시스템 버스를 개념적으로 구분하면 다음과 같습니다.

**컴퓨터 내부의 데이터 흐름**

```text
              ┌─────────────────────┐
              │         CPU         │
              │                     │
              │  ┌─────┐ ┌───────┐  │
              │  │ ALU │ │제어장치│  │
              │  └─────┘ └───────┘  │
              │      레지스터       │
              └──────────┬──────────┘
                         │
                  시스템 버스
             ┌───────────┼───────────┐
             │           │           │
             ▼           ▼           ▼
         ┌───────┐  ┌────────┐  ┌────────┐
         │  RAM  │  │ 저장장치│  │입출력장치│
         └───────┘  └────────┘  └────────┘
```

- CPU : 명령어를 해석하고 실행
- RAM : 실행 중인 명령어와 데이터 보관
- 저장장치 : 프로그램과 파일을 장기 보관
- 입출력장치 : 외부와 데이터 교환

※ 실제 하드웨어에서는 메모리 컨트롤러와
I/O 인터페이스 등을 통해 연결된다.

- **주소 버스:** 어느 위치에 접근할지 알려 주는 주소 전달
- **데이터 버스:** 실제 데이터와 명령어 전달
- **제어 버스:** 읽기·쓰기·인터럽트 등의 제어 신호 전달

**실행 흐름 예시:** 저장장치에 있는 프로그램을 실행하면 운영체제가 필요한 내용을 메모리에 올리고, CPU는 메모리에서 명령어를 읽어 실행합니다. 화면 출력이 필요하면 입출력장치를 통해 결과를 보여 줍니다.

### ✅ Chapter01 핵심 정리

- **CPU는 실행, 메모리는 실행 중 보관, 보조기억장치는 장기 보관**을 담당합니다.
- 데이터는 처리 대상, 명령어는 처리 방법입니다.
- 프로그램 실행을 이해하려면 부품 자체보다 **부품 간 데이터 이동**을 함께 보아야 합니다.

## Chapter02. 데이터
<details>
<summary>핵심 개념 펼치기</summary>

### 1. 0과 1로 정보를 표현하는 이유

디지털 회로는 서로 구별하기 쉬운 두 상태를 이용합니다. 이를 **비트(bit)**의 `0`과 `1`로 표현합니다. `n`비트는 총 **2ⁿ개 서로 다른 상태**를 표현할 수 있습니다. **1바이트(byte) = 8비트**이며, 8비트에는 256가지 비트 패턴이 있습니다.

- **1 KB = 1,000 B**, **1 KiB = 1,024 B**: 십진 단위와 이진 단위는 다릅니다.
- 같은 비트 패턴도 **정수인지, 문자 코드인지**에 따라 의미가 달라집니다.

### 2. 이진수·십육진수·음수

이진수의 각 자릿값은 오른쪽부터 `1, 2, 4, 8, ...`입니다.

```text
이진수 1011₂ = 1×8 + 0×4 + 1×2 + 1×1 = 11₁₀
십육진수 B₁₆ = 11₁₀
이진수 1111 0000₂ = F0₁₆  (4비트마다 16진수 한 자리)
```

**2의 보수**는 정해진 비트 수 안에서 음수를 표현하는 대표적인 방식입니다. 8비트에서 `+5 = 0000 0101`이고, 비트를 뒤집은 뒤 1을 더하면 `-5 = 1111 1011`입니다. 따라서 8비트 부호 있는 정수의 표현 범위는 **-128~127**입니다. 비트 수가 정해져 있으므로 범위를 넘으면 **오버플로우**가 발생할 수 있습니다.

### 3. 문자 집합과 문자 인코딩

- **문자 집합:** 사용할 문자들의 목록과 문자에 부여한 식별값
- **인코딩:** 문자 식별값을 저장·전송할 바이트들로 변환하는 규칙
- **디코딩:** 바이트를 다시 문자로 해석하는 과정

| 방식 | 핵심 |
|---|---|
| ASCII | 영어·숫자·기호 등 기본 문자에 7비트 값 부여 |
| EUC-KR | 한글을 포함한 기존 문자 인코딩 방식 |
| Unicode | 세계 여러 문자의 고유한 코드 포인트를 정의하는 표준 |
| UTF-8 | Unicode 코드 포인트를 **1~4바이트**로 인코딩 |

예를 들어 영문 `A`는 UTF-8에서 `41`(16진수, 1바이트)로 저장되지만, 한글 `가`는 `EA B0 80`(3바이트)로 저장됩니다.

**주의:** Unicode와 UTF-8은 같은 뜻이 아닙니다. **Unicode는 문자 식별 체계**, **UTF-8은 인코딩 방식**입니다. 저장한 방식과 읽는 방식이 다르면 글자가 깨질 수 있습니다.

***확인할 개념: 10진수 42를 다른 진법으로 표시하고, 문자 가가 UTF-8 바이트로 인코딩되는 과정을 확인한다.***

```java
import java.nio.charset.StandardCharsets;
import java.util.HexFormat;

public class Chapter02DataEncoding {
    public static void main(String[] args) {
        int number = 42;
        System.out.println("10진수: " + number);
        System.out.println("2진수: " + Integer.toBinaryString(number));
        System.out.println("16진수: " + Integer.toHexString(number));

        byte[] bytes = "가".getBytes(StandardCharsets.UTF_8);
        System.out.println("UTF-8 바이트: " + HexFormat.of().formatHex(bytes));
        System.out.println("디코딩: " + new String(bytes, StandardCharsets.UTF_8));
    }
}
```

주의: 숫자의 진법 변환과 문자 인코딩은 서로 다른 개념이다.

### ✅ Chapter02 핵심 정리

- 비트는 정보 표현의 기본 단위이고, 자릿수에 따라 표현 가능한 값의 수가 달라집니다.
- 음수 표현에는 2의 보수가 널리 사용됩니다.
- 문자 깨짐을 이해하려면 **문자 집합 → 인코딩 → 바이트 저장 → 디코딩** 순서를 알아야 합니다.

## Chapter03. 명령어
<details>
<summary>핵심 개념 펼치기</summary>

### 1. 소스 코드가 CPU 명령어가 되기까지

사람이 읽기 좋은 Java·C 등의 코드는 **고급 언어**입니다. CPU가 직접 실행하는 것은 해당 CPU의 **명령어 집합 구조(ISA)**에 맞는 **기계어**입니다. 기계어를 사람이 읽기 쉽게 기호로 표현한 언어가 **어셈블리어**입니다.

- **컴파일:** 소스 코드를 다른 코드(기계어 또는 중간 코드 등)로 변환
- **인터프리트:** 실행 시 해석·실행하는 방식
- 두 방식은 **혼합**될 수 있습니다. Java는 소스를 바이트코드로 컴파일한 뒤 JVM에서 이를 인터프리트하거나 JIT 컴파일해 실행할 수 있습니다.

### 2. 명령어의 기본 구조

명령어는 개념적으로 **연산 코드(Opcode)**와 **오퍼랜드(Operand)**로 구성됩니다.

```text
ADD R1, R2
 └┬┘ └─┬─┘
연산 코드  오퍼랜드
```

- 연산 코드: 덧셈, 이동, 비교, 분기 등 **무엇을 할지** 지정
- 오퍼랜드: 값이나 레지스터, 메모리 위치 등 **무엇을 대상으로 할지** 지정
- 실제 명령어 형식과 지원하는 연산은 CPU 아키텍처에 따라 다릅니다.

### 3. 주소 지정 방식(Addressing Mode)

CPU가 필요한 데이터를 **어디서 가져올지** 결정하는 규칙입니다.

| 방식 | 데이터 위치를 결정하는 방법 | 예시 의미 |
|---|---|---|
| 즉시 주소 지정 | 명령어 안에 값이 직접 존재 | `5` 사용 |
| 직접 주소 지정 | 명령어에 메모리 주소 존재 | 주소 100번지의 값 사용 |
| 간접 주소 지정 | 지정한 위치에 **실제 주소** 존재 | 한 번 더 따라가 값 읽기 |
| 레지스터 주소 지정 | 레지스터에 값 존재 | R1의 값 사용 |
| 레지스터 간접 주소 지정 | 레지스터에 메모리 주소 존재 | R1이 가리키는 위치 읽기 |

**주소 지정 방식별 데이터 접근 구조**

```text
[1] 즉시 주소 지정
명령어 [값: 7]
       └──────────────→ 데이터 7

[2] 직접 주소 지정
명령어 [주소: 100]
       └──→ 메모리[100] = 7
                         └──→ 데이터 7

[3] 간접 주소 지정
명령어 [주소: 100]
       └──→ 메모리[100] = 200
                         └──→ 메모리[200] = 7
                                            ↓
                                         데이터 7

[4] 레지스터 주소 지정
명령어 [R1]
       └──→ R1 = 7
                  └──→ 데이터 7

[5] 레지스터 간접 주소 지정
명령어 [R1]
       └──→ R1 = 200
                  └──→ 메모리[200] = 7
                                      ↓
                                   데이터 7
```

**핵심 차이**

- 즉시 주소 지정 : 명령어 자체에 데이터가 존재
- 직접 주소 지정 : 메모리 주소를 이용해 데이터 접근
- 간접 주소 지정 : 메모리에서 주소를 한 번 더 확인
- 레지스터 주소 지정 : 레지스터 값을 직접 사용
- 레지스터 간접 주소 지정 : 레지스터에 저장된 주소로 메모리에 접근

**왜 중요할까?** 같은 덧셈도 **명령어에 들어 있는 수**를 더하는 것과 **메모리에서 가져온 수**를 더하는 것은 데이터 접근 과정과 실행 비용이 다를 수 있습니다.

### ✅ Chapter03 핵심 정리

- **고급 언어 → 변환/실행 환경 → CPU 명령어**의 관계를 이해합니다.
- 연산 코드는 **무엇을**, 주소 지정 방식은 **어디에 있는 데이터로** 수행할지 결정합니다.
- ISA는 CPU가 이해할 수 있는 명령어의 규칙입니다.

## Chapter04. CPU와 작동 원리
<details>
<summary>핵심 개념 펼치기</summary>

### 1. ALU와 제어장치

- **ALU(산술논리연산장치):** 덧셈·비교·AND 같은 연산을 수행하고 결과 및 상태 플래그를 생성합니다.
- **제어장치:** 명령어를 해석하고 레지스터·ALU·메모리 등으로 제어 신호를 보냅니다.
- **플래그:** 연산 결과가 0인지, 오버플로우가 일어났는지 등의 상태를 나타낼 수 있습니다.

### 2. 주요 레지스터의 역할

| 레지스터 | 저장하는 정보 |
|---|---|
| **PC(프로그램 카운터)** | 다음에 인출할 명령어의 주소 |
| **IR(명령어 레지스터)** | 현재 인출·해석 중인 명령어 |
| **MAR(메모리 주소 레지스터)** | 접근하려는 메모리 주소 |
| **MDR(메모리 데이터 레지스터)** | 메모리와 주고받는 데이터 |
| 범용 레지스터 | 연산 데이터·주소 등 |
| 플래그 레지스터 | 비교·산술 결과의 상태 |
| 스택 포인터(SP) | 현재 스택 위치 |

> 레지스터의 정확한 종류와 명칭은 CPU마다 다르며, 위 표는 동작 원리 설명을 위한 대표적인 모델입니다.

### 3. 스택과 변위 주소 지정

**스택(Stack)**은 나중에 넣은 데이터를 먼저 꺼내는 **LIFO(후입선출)** 구조입니다. **스택 포인터(SP)**는 스택의 현재 위치를 가리키며, 함수 호출·복귀 정보를 다루는 데 사용됩니다. **변위 주소 지정**은 기준 레지스터 값에 일정한 값을 더해 유효 주소를 계산하는 방식입니다. 예를 들어 기준 주소가 `1000`, 변위가 `24`라면 접근 대상 주소는 `1024`가 됩니다.

### 4. 명령어 사이클: 인출 → 해석 → 실행

```text
① PC가 다음 명령어 주소를 가리킴
② 메모리에서 명령어를 인출하고 IR에 저장
③ 제어장치가 명령어를 해석
④ 필요한 데이터를 읽고 ALU 등에서 실행
⑤ 결과를 저장하고 다음 명령어 처리
```

**CPU 내부 명령어 처리 흐름**

```text
         ┌─────────────────┐
         │ PC              │
         │ 다음 명령어 주소 │
         └────────┬────────┘
                  │ 주소 전달
                  ▼
         ┌─────────────────┐
         │ MAR             │
         │ 메모리 접근 주소│
         └────────┬────────┘
                  │
                  ▼
         ┌─────────────────┐
         │ 메모리(RAM)     │
         │ 명령어 읽기     │
         └────────┬────────┘
                  │
                  ▼
         ┌─────────────────┐
         │ MDR             │
         │ 읽어 온 데이터  │
         └────────┬────────┘
                  │
                  ▼
         ┌─────────────────┐
         │ IR              │
         │ 현재 명령어     │
         └────────┬────────┘
                  │
                  ▼
         ┌─────────────────┐
         │ 제어장치        │
         │ 명령어 해석     │
         └────────┬────────┘
                  │
                  ▼
         ┌─────────────────┐
         │ ALU / 레지스터  │
         │ 명령어 실행     │
         └─────────────────┘
```

※ 대표적인 CPU 동작을 단순화한 모델이다.
실제 레지스터 구성과 데이터 이동 경로는 CPU마다 다르다.

분기 명령어가 실행되면 **PC의 값이 변경**되어 다른 명령어로 이동할 수 있습니다. 모든 명령어가 매번 같은 단계를 동일하게 거치는 것은 아니지만, 이 흐름을 알면 CPU가 코드를 실행하는 원리를 이해할 수 있습니다.

***확인할 개념: PC로 다음 명령어를 선택하고, 명령어를 해석하여 가상의 레지스터 값을 변경한다.***

```java
public class Chapter04InstructionCycle {
    public static void main(String[] args) {
        String[] program = {"LOAD 5", "ADD 3", "SUB 2", "HALT"};
        int pc = 0;          // 다음에 읽을 명령어의 위치
        int accumulator = 0; // 연산 결과를 저장하는 가상 레지스터

        while (pc < program.length) {
            String instruction = program[pc++]; // 인출(Fetch)
            String[] parts = instruction.split(" "); // 해석(Decode)

            switch (parts[0]) { // 실행(Execute)
                case "LOAD" -> accumulator = Integer.parseInt(parts[1]);
                case "ADD" -> accumulator += Integer.parseInt(parts[1]);
                case "SUB" -> accumulator -= Integer.parseInt(parts[1]);
                case "HALT" -> {
                    System.out.println("최종 결과: " + accumulator); // 6
                    return;
                }
                default -> throw new IllegalArgumentException("알 수 없는 명령어");
            }
        }
    }
}
```

주의: 실제 CPU를 제어하는 코드가 아니라 인출 → 해석 → 실행을 모방한 시뮬레이션이다.


### 5. 인터럽트와 예외

**인터럽트**는 CPU가 현재 실행 흐름 외에 처리해야 할 사건이 생겼음을 알려 줍니다.

- **하드웨어 인터럽트:** 입출력장치가 작업 완료 등을 알림
- **동기적 예외:** 명령어 실행 중 발생한 사건(예: 유효하지 않은 연산, 페이지 폴트)
- 처리 과정: 현재 상태 저장 → 적절한 처리 루틴 실행 → 필요 시 이전 실행 흐름 복원

**핵심 연결:** 입출력 완료를 CPU가 계속 확인하는 대신, 장치가 **인터럽트로 알려 줄 수 있다**는 점이 Chapter08의 입출력 방식과 연결됩니다.

### ✅ Chapter04 핵심 정리

- CPU는 **레지스터에 정보를 두고, 제어장치의 신호에 따라 ALU 등에서 명령어를 실행**합니다.
- PC와 IR의 역할, 명령어 사이클의 흐름을 구분해야 합니다.
- 인터럽트는 현재 흐름에서 다른 처리가 필요한 상황에 대응하게 합니다.

## Chapter05. CPU 성능 향상 기법
<details>
<summary>핵심 개념 펼치기</summary>

### 1. 클럭·코어·스레드

- **클럭 주파수:** CPU 동작의 기준 신호가 단위 시간에 반복되는 횟수입니다. 높다고 항상 성능이 비례해 올라가지는 않습니다.
- **코어(Core):** 명령어를 실행하는 처리 핵심. 여러 코어는 여러 작업을 병렬로 처리하는 데 도움이 됩니다.
- **하드웨어 스레드:** 하나의 코어가 여러 명령어 흐름의 상태를 관리해 자원을 활용하는 방식입니다.
- **소프트웨어 스레드:** 운영체제가 스케줄링하는 실행 흐름이며 하드웨어 스레드와 구분해야 합니다.

### 2. 명령어 파이프라이닝

한 명령어의 **인출·해석·실행**을 각각 다른 단계로 나누면 여러 명령어의 단계를 **겹쳐 수행**할 수 있습니다.

```text
시각      1     2     3     4
명령어 A  인출  해석  실행
명령어 B        인출  해석  실행
명령어 C              인출  해석  실행
```

파이프라이닝은 단일 명령어의 지연 시간을 반드시 줄이는 것이 아니라 **단위 시간당 완료하는 명령어 수(처리량)**를 늘리는 방식입니다.

**파이프라인 위험(Hazard)**
- **데이터 위험:** 앞 명령어의 결과가 아직 나오지 않았는데 뒤 명령어가 이를 필요로 함
- **제어 위험:** 분기 결과가 확정되기 전 다음 명령어를 정하기 어려움
- **구조적 위험:** 여러 단계가 같은 하드웨어 자원을 동시에 요구

### 3. 슈퍼스칼라와 비순차적 실행

- **슈퍼스칼라:** 여러 실행 장치를 활용해 한 번에 여러 명령어를 발행·처리합니다.
- **비순차적 실행(Out-of-Order):** 데이터 의존성이 허용하는 범위에서 준비된 명령어를 먼저 실행하여 유휴 시간을 줄입니다.

### 4. CISC와 RISC

| 구분 | CISC | RISC |
|---|---|---|
| 설계 방향 | 다양하고 비교적 복잡한 명령어 | 비교적 단순하고 규칙적인 명령어 |
| 명령어 길이 | 가변 길이인 경우가 많음 | 고정 길이인 경우가 많음 |
| 대표 계열 | x86 | ARM, RISC-V |

**주의:** CISC = 느림, RISC = 빠름이라는 단순 구분은 틀립니다. 실제 성능은 구현 기술, 캐시, 클럭, 실행 장치 등에 함께 좌우됩니다.

### ✅ Chapter05 핵심 정리

- 성능은 **클럭만으로 결정되지 않으며**, 코어 수와 명령어 처리 효율이 함께 중요합니다.
- 파이프라인은 실행 단계를 겹쳐 **처리량**을 높입니다.
- CISC와 RISC는 **명령어 집합의 설계 방향**을 구분하는 개념입니다.

</details>

## Chapter06. 메모리와 캐시 메모리
<details>
<summary>핵심 개념 펼치기</summary>

### 1. RAM의 역할과 종류

RAM은 CPU가 곧 사용할 **명령어와 데이터**를 보관하는 주기억장치입니다. 일반적인 RAM은 전원이 꺼지면 데이터가 사라지는 **휘발성 메모리**입니다.

| 종류 | 특징 | 주된 활용 |
|---|---|---|
| **DRAM** | 내용을 유지하기 위한 주기적 재충전 필요 | 일반적인 주기억장치 |
| **SRAM** | 재충전이 필요하지 않으며 빠르고 비용이 높음 | CPU 캐시 등에 활용 |
| **SDRAM** | 클럭에 맞추어 동작하는 DRAM | 주기억장치 |
| **DDR SDRAM** | 클럭의 두 에지에서 데이터를 전송 | 현대 주기억장치 |

RAM 용량이 부족하면 메모리 확보를 위해 저장장치를 더 자주 이용해야 할 수 있습니다. **용량**과 **접근 속도**는 별개의 성능 요소입니다.

### 2. 논리 주소와 물리 주소

- **논리 주소(가상 주소):** 프로그램이 사용하는 주소
- **물리 주소:** 실제 RAM 위치를 가리키는 주소
- **MMU:** 논리/가상 주소를 물리 주소로 변환하는 하드웨어

```text
프로그램이 주소 100에 접근 요청
   ↓ 주소 변환·보호 검사
MMU → 실제 RAM의 해당 위치에 접근
```

주소 변환 덕분에 프로그램은 실제 RAM의 배치를 직접 알 필요가 없고, 운영체제는 프로그램이 남의 메모리에 함부로 접근하지 못하도록 보호할 수 있습니다. 교재의 **베이스/한계 레지스터 방식**은 주소 변환과 보호를 설명하는 기본 모델입니다. 현대 시스템의 페이징은 Chapter14에서 다룹니다.

### 3. 저장장치 계층 구조와 캐시

일반적으로 CPU에 가까울수록 **빠르고 비싸며 용량은 작습니다**.

```text
레지스터 → CPU 캐시(L1/L2/L3) → RAM → SSD/HDD
  매우 빠름                               상대적으로 느림
```

**캐시(Cache)**는 가까운 시일 내에 사용할 가능성이 높은 데이터를 미리 복사해 두는 저장 공간입니다.

- **캐시 적중(Hit):** 필요한 정보가 캐시에 있어 빠르게 접근
- **캐시 미스(Miss):** 캐시에 없어 RAM 등 하위 계층에서 가져옴

### 4. 참조 지역성(Locality)

- **시간 지역성:** 방금 사용한 데이터를 다시 사용할 가능성이 높음(반복문에서 같은 변수 사용)
- **공간 지역성:** 접근한 주소 주변도 사용할 가능성이 높음(배열의 인접 요소 순회)

**예시:** 배열을 처음부터 연속으로 읽으면 인접 데이터가 함께 캐시에 들어와 효과를 볼 수 있습니다. 반대로 메모리의 서로 멀리 떨어진 위치를 무작위로 접근하면 캐시 효율이 떨어질 수 있습니다.

***확인할 개념: 연속된 인덱스가 같은 메모리 블록에 속하면 캐시 적중이 이어질 수 있음을 확인한다.***

```java
public class Chapter06CacheLocality {
    public static void main(String[] args) {
        int[] accessedIndexes = {0, 1, 2, 3, 8, 9, 0};
        int elementsPerBlock = 4;
        int cachedBlock = -1; // 한 번에 블록 하나만 저장하는 가상 캐시

        for (int index : accessedIndexes) {
            int block = index / elementsPerBlock;
            boolean hit = (block == cachedBlock);
            System.out.printf("인덱스 %d → %s%n", index, hit ? "HIT" : "MISS");
            if (!hit) cachedBlock = block;
        }
    }
}
```

주의: 블록 하나만 저장하는 교육용 가상 캐시이며 실제 CPU 캐시 정책과는 다르다.


### ✅ Chapter06 핵심 정리

- RAM은 프로그램 실행 중 데이터를 저장하고, 캐시는 CPU와 RAM의 속도 차이를 완화합니다.
- **논리 주소 → 주소 변환 → 물리 주소**를 구분해야 합니다.
- 시간·공간 지역성은 캐시가 효과적인 중요한 이유입니다.

</details>

## Chapter07. 보조기억장치
<details>
<summary>핵심 개념 펼치기</summary>

### 1. HDD와 플래시 메모리

**보조기억장치**는 전원이 꺼져도 데이터를 유지하는 비휘발성 저장 공간입니다.

**HDD(하드 디스크)**
- 회전하는 **플래터**의 자기 상태를 이용해 데이터 저장
- **트랙**과 **섹터** 단위로 위치를 구분하고 **헤드**로 읽고 씀
- 접근 시간에는 **탐색 시간(헤드 이동)** + **회전 지연(원하는 섹터 대기)** + **전송 시간**이 관여

**플래시 메모리(SSD, USB 등)**
- 전하 상태를 이용해 데이터를 저장하고 기계적 회전 부품이 없음
- 일반적으로 **페이지 단위 읽기·쓰기**, **블록 단위 삭제**라는 제약이 있음
- 셀당 저장 비트 수에 따라 SLC(1비트), MLC(2비트), TLC(3비트) 등으로 구분 가능

**핵심 차이:** HDD는 회전·이동에 따른 지연이 있고, SSD는 기계적 탐색 지연이 없어 무작위 접근에서 유리한 경우가 많습니다.

### 2. RAID: 여러 디스크를 하나처럼 사용

RAID는 여러 저장장치에 데이터를 **분산하거나 중복 저장**하여 성능 또는 장애 대응 능력을 높이는 방법입니다.

| 방식 | 데이터 저장 방식 | 주의점 |
|---|---|---|
| **RAID 0** | 데이터를 여러 디스크에 나눠 저장(스트라이핑) | 디스크 하나만 고장 나도 데이터 유실 위험 |
| **RAID 1** | 동일 데이터 복제(미러링) | 용량 효율이 낮아짐 |
| **RAID 4** | 데이터는 분산, 패리티는 전용 디스크 | 패리티 디스크에 부하 집중 가능 |
| **RAID 5** | 데이터와 패리티를 디스크들에 분산 | 일반적으로 디스크 1개 장애 대응 |
| **RAID 6** | 이중 패리티 사용 | 일반적으로 디스크 2개 장애 대응 |

**RAID 0 / RAID 1 / RAID 5 저장 구조**

```text
RAID 0 : 스트라이핑 (데이터 분산)

Disk A       Disk B
┌─────┐      ┌─────┐
│ D1  │      │ D2  │
├─────┤      ├─────┤
│ D3  │      │ D4  │
├─────┤      ├─────┤
│ D5  │      │ D6  │
└─────┘      └─────┘

→ 데이터를 나누어 저장
→ 중복 보호가 없어 디스크 장애에 취약


RAID 1 : 미러링 (데이터 복제)

Disk A       Disk B
┌─────┐      ┌─────┐
│ D1  │      │ D1  │
├─────┤      ├─────┤
│ D2  │      │ D2  │
├─────┤      ├─────┤
│ D3  │      │ D3  │
└─────┘      └─────┘

→ 동일 데이터를 복제하여 저장
→ 디스크 장애에 대비 가능


RAID 5 : 분산 패리티

Disk A       Disk B       Disk C
┌─────┐      ┌─────┐      ┌─────┐
│ D1  │      │ D2  │      │ P1  │
├─────┤      ├─────┤      ├─────┤
│ D3  │      │ P2  │      │ D4  │
├─────┤      ├─────┤      ├─────┤
│ P3  │      │ D5  │      │ D6  │
└─────┘      └─────┘      └─────┘

D = 데이터 블록
P = 해당 데이터 묶음의 패리티

→ 데이터와 패리티를 여러 디스크에 분산
→ 일반적으로 디스크 1개 장애까지 대응 가능
```

**패리티(Parity)**는 장애가 난 디스크의 데이터를 복구하는 데 이용할 수 있는 추가 정보입니다. 다만 RAID 구성만으로 파일 오삭제나 랜섬웨어를 막을 수는 없습니다. **RAID와 백업은 별개**입니다.

***확인할 개념: 두 데이터 블록의 XOR 패리티를 계산하고, 하나의 블록과 패리티로 다른 블록을 복원한다.***

```java
public class Chapter07RaidParity {
    public static void main(String[] args) {
        int diskA = 0b1010;
        int diskB = 0b1100;
        int parity = diskA ^ diskB;       // XOR 패리티 생성
        int recoveredB = diskA ^ parity; // B 디스크 데이터 복원

        System.out.println("패리티: " + Integer.toBinaryString(parity)); // 110
        System.out.println("복원된 B: " + Integer.toBinaryString(recoveredB)); // 1100
    }
}
```

주의: RAID 5의 패리티 원리를 단순화한 예시이며 실제 디스크 구성·장애 복구를 구현하지 않는다.


### ✅ Chapter07 핵심 정리

- HDD는 자기 디스크, SSD는 주로 플래시 메모리로 데이터를 보관합니다.
- 저장장치의 **접근 지연**과 **데이터 유지 방식**을 구분합니다.
- RAID는 분산·복제로 성능과 가용성을 조절하며, **백업을 대체하지 않습니다**.

</details>

## Chapter08. 입출력장치
<details>
<summary>핵심 개념 펼치기</summary>

### 1. 장치 컨트롤러와 드라이버

입출력장치는 CPU보다 느리거나 동작 방식이 다를 수 있습니다. CPU가 모든 장치의 세부 규칙을 직접 처리하면 부담이 커집니다.

- **장치 컨트롤러(하드웨어):** 장치 동작 제어, 데이터 버퍼링, 상태·오류 정보 관리
- **장치 드라이버(소프트웨어):** 운영체제가 해당 장치를 사용할 수 있도록 명령과 결과를 연결

**동작 예시:** 프로그램이 파일 읽기를 요청 → 운영체제가 장치 드라이버를 통해 작업 지시 → 컨트롤러가 저장장치와 통신 → 완료 결과를 운영체제에 알림.

### 2. 세 가지 입출력 방식

| 방식 | CPU의 역할 | 특징 |
|---|---|---|
| **프로그램 입출력** | 장치 상태를 확인하며 데이터 전송 | 반복 확인(폴링)으로 CPU 시간 사용 가능 |
| **인터럽트 기반 입출력** | 다른 일을 하다가 완료 신호에 대응 | 장치가 필요한 시점에 알림 |
| **DMA 입출력** | 전송 설정 및 완료 처리에 주로 관여 | 컨트롤러가 메모리↔장치 사이 대량 데이터 전송 담당 |

### 3. DMA(Direct Memory Access) 처리 흐름

```text
① CPU가 DMA 컨트롤러에 전송 위치·크기 등을 설정
② DMA 컨트롤러가 장치와 메모리 사이 데이터를 전송
③ 전송 완료(또는 오류)를 인터럽트 등으로 알림
④ CPU가 완료 결과를 처리
```

DMA는 CPU가 데이터의 매 단위를 직접 옮기는 부담을 줄일 수 있습니다. **CPU가 완전히 관여하지 않는다는 뜻은 아닙니다.**

### ✅ Chapter08 핵심 정리

- **컨트롤러는 하드웨어**, **드라이버는 소프트웨어**입니다.
- 인터럽트는 완료를 알리는 방식이고, DMA는 **데이터 전송 작업을 분담**하는 방식입니다.
- 입출력 효율을 이해하려면 CPU·메모리·장치 간 역할 분담을 보아야 합니다.

</details>

# PART 02. 운영체제 (Operating System)

## Chapter09. 운영체제 시작하기
<details>
<summary>핵심 개념 펼치기</summary>

### 1. 운영체제가 왜 필요할까?

CPU는 계산을, 메모리는 저장을, 입출력장치는 정보 교환을 수행합니다. 그런데 프로그램 여러 개가 동시에 CPU나 메모리를 사용하려고 하면 **누구에게 언제 얼마만큼 배분할지** 결정해야 합니다. 이 역할을 담당하는 핵심 소프트웨어가 **운영체제(OS)**입니다.

운영체제는 프로그램에 실행 환경을 제공하고 CPU·메모리·파일·입출력장치 같은 자원을 **관리·보호**합니다.

### 2. 커널(Kernel)과 운영체제 서비스

- **커널:** 운영체제의 핵심으로 자원 관리, 프로세스 관리, 메모리 보호 등을 담당합니다.
- **운영체제 서비스:** 파일 열기, 프로세스 생성, 메모리 할당, 장치 접근 등을 프로그램에 제공하는 기능입니다.
- 운영체제 전체를 커널과 완전히 같은 뜻으로 사용할 수는 없습니다. 사용자 인터페이스 등은 커널 외부에서 제공될 수 있습니다.

### 3. 사용자 모드와 커널 모드

실수나 악의적인 코드가 운영체제나 다른 프로그램을 망가뜨리지 않도록, CPU는 접근 권한이 다른 실행 모드를 지원합니다.

| 모드 | 실행 주체의 권한 | 주요 동작 |
|---|---|---|
| **사용자 모드(User Mode)** | 제한된 권한 | 일반 응용 프로그램 실행 |
| **커널 모드(Kernel Mode)** | 특권 명령 실행 가능 | 메모리 관리, 장치 제어 등의 커널 작업 |

일반 프로그램이 파일을 읽고 싶다고 **디스크를 임의로 직접 제어하는 것**이 아니라, 운영체제에 요청해야 하는 이유가 여기 있습니다.

### 4. 시스템 호출(System Call)

**시스템 호출**은 사용자 프로그램이 운영체제의 서비스를 이용하기 위해 제공하는 공식적인 진입 경로입니다.

```text
사용자 프로그램: 파일 읽기 요청
   ↓ 시스템 호출
커널 모드: 접근 권한 확인 및 파일 시스템·드라이버 처리
   ↓ 처리 결과 반환
사용자 모드: 읽은 데이터 이용
```

시스템 호출 시에는 운영체제 코드가 실행될 수 있도록 모드 전환이 이루어집니다. 이러한 전환은 단순한 **일반 함수 호출과 다릅니다**. 다만 모든 함수 호출이 시스템 호출인 것은 아닙니다.

### ✅ Chapter09 핵심 정리

- 운영체제는 **자원 관리 + 프로그램 실행 서비스 + 보호**를 맡습니다.
- 커널은 운영체제의 핵심이며, 응용 프로그램은 보통 제한된 사용자 모드에서 실행됩니다.
- 시스템 호출은 프로그램이 **커널의 서비스를 요청하는 통로**입니다.

</details>

## Chapter10. 프로세스와 스레드
<details>
<summary>핵심 개념 펼치기</summary>

### 1. 프로그램과 프로세스의 차이

- **프로그램(Program):** 저장장치에 있는 실행 가능한 명령어·데이터
- **프로세스(Process):** 메모리에 적재되어 **실행 중이거나 실행을 위해 관리되는 프로그램의 인스턴스**

같은 프로그램을 두 번 실행하면 서로 다른 프로세스가 만들어질 수 있습니다. 각 프로세스는 운영체제가 구분하여 관리합니다.

### 2. PCB(프로세스 제어 블록)

운영체제는 각 프로세스의 상태를 기록해야 합니다. 이를 위한 관리 자료구조가 **PCB(Process Control Block)**입니다.

| PCB의 대표 정보 | 의미 |
|---|---|
| PID | 프로세스 식별 번호 |
| 프로세스 상태 | 준비·실행·대기 등 |
| PC 및 레지스터 정보 | 다음 명령어와 중단 당시 CPU 상태 |
| 스케줄링 정보 | 우선순위, 큐 관련 정보 등 |
| 메모리·자원 정보 | 메모리 관리 정보, 열린 파일 등 |

### 3. 프로세스 상태와 문맥 교환

```text
생성 → 준비(Ready) → 실행(Running) → 종료
          ↑          ↓
          └── 대기(Waiting) ← 입출력 등 대기 사건
```

- **준비:** 실행할 수 있으나 CPU 할당을 기다리는 상태
- **실행:** 실제로 CPU를 사용 중인 상태
- **대기:** 입출력 완료 같은 사건을 기다리는 상태

**문맥 교환(Context Switch)**은 CPU에서 실행할 대상을 바꾸기 위해 이전 실행 상태를 저장하고 다음 실행 상태를 복원하는 과정입니다.

```text
프로세스 A 실행 → A의 PC·레지스터 상태 저장
                   ↓
             B의 실행 상태 복원
                   ↓
                프로세스 B 실행
```

문맥 교환 중에는 실행 대상을 바꾸기 위한 관리 작업이 이루어지므로 **오버헤드**가 발생합니다.

### 4. 프로세스 메모리 영역

전형적인 프로세스 주소 공간을 개념적으로 나누면 다음과 같습니다.

| 영역 | 주로 저장되는 것 |
|---|---|
| 코드(Text) | 실행할 명령어 |
| 데이터(Data) | 전역 변수·정적 변수 등 |
| 힙(Heap) | 동적으로 확보한 메모리 |
| 스택(Stack) | 함수 호출 정보·지역 변수 등 |

> 실제 메모리 배치와 관리 방식은 언어 실행 환경과 운영체제에 따라 달라질 수 있습니다.

### 5. 프로세스 계층 구조와 생성

일부 운영체제는 새 프로세스를 만든 프로세스를 **부모 프로세스**, 만들어진 프로세스를 **자식 프로세스**라고 부르며 계층적으로 관리합니다. 유닉스 계열에서는 `fork()`로 자식 프로세스를 만들고 `exec()` 계열 호출로 실행할 프로그램을 바꿀 수 있습니다. 부모와 자식은 서로 다른 프로세스이므로, **한 프로세스의 일반 변수 수정이 다른 프로세스의 변수에 자동으로 반영되지는 않습니다.**

### 6. 스레드(Thread)와 멀티스레드

**스레드**는 프로세스 안의 실행 흐름입니다. 같은 프로세스의 스레드들은 일반적으로 **코드·힙·전역 데이터**를 공유하지만, 각자 **PC·레지스터 실행 상태·스택**을 가집니다.


**프로세스와 스레드의 메모리 공유 구조**

```text
┌──────────────────────────────────┐
│            Process A             │
│                                  │
│   ┌──────────────────────────┐   │
│   │      공유 메모리 영역     │   │
│   │                          │   │
│   │  Code / Data / Heap      │   │
│   └──────────────────────────┘   │
│                ▲                 │
│          공유하여 접근            │
│         ┌──────┴──────┐          │
│         │             │          │
│   ┌─────┴─────┐ ┌─────┴─────┐    │
│   │ Thread 1  │ │ Thread 2  │    │
│   │           │ │           │    │
│   │ PC        │ │ PC        │    │
│   │ Registers │ │ Registers │    │
│   │ Stack     │ │ Stack     │    │
│   └───────────┘ └───────────┘    │
└──────────────────────────────────┘

┌──────────────────────────────────┐
│            Process B             │
│                                  │
│   별도의 가상 주소 공간 사용       │
└──────────────────────────────────┘
```

**핵심**

- 서로 다른 프로세스는 기본적으로 주소 공간이 분리된다.
- 같은 프로세스의 스레드는 코드·힙·전역 데이터를 공유한다.
- 각 스레드는 독립적인 PC, 레지스터 상태, 스택을 가진다.
- 공유 메모리 접근 시 경쟁 상태가 발생할 수 있다.


| 구분 | 멀티프로세스 | 멀티스레드 |
|---|---|---|
| 주소 공간 | 보통 프로세스별 분리 | 같은 프로세스 내부 공간 공유 |
| 데이터 교환 | 프로세스 간 통신(IPC) 등이 필요 | 공유 메모리 이용 가능 |
| 주의점 | 통신·전환 비용 고려 | 공유 데이터 경쟁 상태 주의 |

**예시:** 웹 브라우저의 여러 작업을 각각의 프로세스로 분리할 수도 있고, 한 프로세스에서 여러 스레드로 작업을 나눌 수도 있습니다. 어떤 구조가 적절한지는 성능·격리·안정성 요구에 따라 달라집니다.

***확인할 개념: 현재 Java 프로세스의 PID를 확인하고, 같은 프로세스 안에서 별도 스레드를 시작·종료한다.***

```java
public class Chapter10ProcessAndThreads {
    public static void main(String[] args) throws InterruptedException {
        System.out.println("현재 프로세스 PID: " + ProcessHandle.current().pid());

        Thread worker = new Thread(() -> {
            System.out.println("작업 스레드: " + Thread.currentThread().getName());
        }, "worker-1");

        worker.start(); // 새로운 실행 흐름 시작
        worker.join();  // 작업 스레드가 끝날 때까지 대기
        System.out.println("메인 스레드 종료");
    }
}
```

주의: `start()`는 새 스레드에서 실행하고, `join()`은 호출한 스레드가 종료를 기다리게 한다.


### ✅ Chapter10 핵심 정리

- 프로그램은 저장된 코드, 프로세스는 **실행을 위해 관리되는 인스턴스**입니다.
- PCB는 프로세스 정보를 관리하고, 문맥 교환은 실행 대상을 바꾸는 과정입니다.
- 스레드는 실행 흐름이며 **공유하는 메모리와 독립적인 실행 상태**를 구분해야 합니다.

## Chapter11. CPU 스케줄링
<details>
<summary>핵심 개념 펼치기</summary>

### 1. 스케줄링이 필요한 이유

CPU 코어 하나는 같은 순간에 제한된 수의 실행 흐름만 실제로 처리할 수 있습니다. 준비 상태의 프로세스가 여러 개라면 운영체제가 **다음에 누구를 실행할지** 선택해야 합니다. 이를 **CPU 스케줄링**이라고 합니다.

운영체제는 **준비 큐(Ready Queue)**와 **대기 큐(Waiting Queue)** 등을 통해 실행 가능한 작업과 특정 사건을 기다리는 작업을 관리합니다. 큐라는 이름이 반드시 단순한 선입선출 순서를 의미하지는 않습니다.

### 2. 성능을 평가하는 기준

| 지표 | 의미 | 일반적 목표 |
|---|---|---|
| CPU 이용률 | 전체 시간 중 CPU가 유용한 작업을 수행한 비율 | 높이기 |
| 처리량(Throughput) | 단위 시간 동안 완료한 작업 수 | 높이기 |
| 반환 시간(Turnaround Time) | 작업 도착부터 완료까지의 시간 | 줄이기 |
| 대기 시간(Waiting Time) | 준비 큐에서 기다린 시간의 합 | 줄이기 |
| 응답 시간(Response Time) | 요청 후 **첫 반응**까지 걸리는 시간 | 줄이기 |

**응답 시간**과 **완료까지 걸린 시간**은 다릅니다. 사용자가 클릭한 뒤 화면이 빨리 반응하더라도 모든 처리가 끝나는 데는 오래 걸릴 수 있습니다.

### 3. 선점형과 비선점형

- **선점형(Preemptive):** 운영체제가 실행 중인 프로세스로부터 CPU를 회수할 수 있음
- **비선점형(Non-preemptive):** 실행 중인 프로세스가 종료되거나 대기 상태로 바뀔 때까지 CPU를 계속 사용

선점형은 응답성에 유리할 수 있지만, 잦은 전환으로 **문맥 교환 비용**이 늘어날 수 있습니다.

### 4. 주요 CPU 스케줄링 알고리즘

| 알고리즘 | 실행 기준 | 장점·주의점 |
|---|---|---|
| **FCFS** | 먼저 도착한 순서 | 간단하지만 긴 작업이 뒤 작업을 지연시킴(호위 효과) |
| **SJF** | CPU 실행 시간이 짧은 작업 우선 | 평균 대기 시간에 유리할 수 있지만 실행 시간 예측이 어려움 |
| **Round Robin(RR)** | 일정 **타임 슬라이스**씩 돌아가며 실행 | 응답성에 유리, 단위 시간이 너무 짧으면 전환 비용 증가 |
| **Priority** | 우선순위 높은 작업 먼저 | 낮은 우선순위 작업이 계속 밀리는 기아 현상 가능 |
| **Multilevel Queue** | 작업 종류별 큐를 구분 | 큐별 정책을 달리할 수 있음 |
| **Multilevel Feedback Queue** | 실행 특성에 따라 큐 사이 이동 | CPU 집중형·입출력 집중형 작업을 구별하여 관리 가능 |


**CPU 스케줄링 실행 순서 비교**

두 프로세스가 시간 0에 동시에 도착했다고 가정한다.

- 프로세스 A : CPU 실행 시간 5
- 프로세스 B : CPU 실행 시간 3
- 문맥 교환에 걸리는 시간은 계산에서 제외

```text
[1] FCFS (선입선출)

시간  0              5        8
      ├──────────────┼────────┤
CPU   │      A       │   B    │
      └──────────────┴────────┘

→ 먼저 도착한 A가 종료될 때까지 실행
→ 이후 B 실행


[2] Round Robin (시간 할당량 = 2)

시간  0     2     4     6   7   8
      ├─────┼─────┼─────┼───┼───┤
CPU   │  A  │  B  │  A  │ B │ A │
      └─────┴─────┴─────┴───┴───┘

→ 각 프로세스가 최대 2만큼 실행
→ 실행이 끝나지 않으면 준비 큐로 이동
→ 다른 프로세스에 CPU 할당
```

**핵심 차이**

- FCFS : 먼저 도착한 작업을 우선 처리
- Round Robin : CPU 시간을 나누어 번갈아 실행
- Round Robin은 응답성을 높일 수 있지만,
  문맥 교환에 따른 오버헤드가 발생할 수 있다.


**RR 예시:** 작업 A, B가 모두 실행 가능하고 타임 슬라이스가 2라면 `A 2만큼 → B 2만큼 → A 2만큼 → ...` 식으로 번갈아 실행합니다. 실제 순서는 도착 시점·대기 사건에 따라 달라집니다.

### 5. 기아 현상과 에이징

- **기아(Starvation):** 어떤 작업이 자원을 오랫동안 할당받지 못하는 현상
- **에이징(Aging):** 오래 기다린 작업의 우선순위를 점차 높여 기아를 완화하는 기법

***확인할 개념: P1의 실행 시간이 5, P2가 3일 때 시간 할당량 2로 번갈아 실행하는 순서를 계산한다.***

```java
public class Chapter11RoundRobin {
    public static void main(String[] args) {
        int[] remaining = {5, 3}; // P1, P2의 남은 CPU 실행 시간
        int quantum = 2;        // 한 번에 최대 2만큼 실행
        int time = 0;

        while (remaining[0] > 0 || remaining[1] > 0) {
            for (int i = 0; i < remaining.length; i++) {
                if (remaining[i] == 0) continue;
                int used = Math.min(quantum, remaining[i]);
                System.out.printf("%d~%d : P%d 실행%n", time, time + used, i + 1);
                time += used;
                remaining[i] -= used;
            }
        }
    }
}
```

주의: 동시 도착·입출력 대기 없음·문맥 교환 비용 0으로 단순화한 스케줄링 시뮬레이션이다.


### ✅ Chapter11 핵심 정리

- CPU 스케줄링은 **여러 준비된 작업 사이의 CPU 배분** 문제입니다.
- **대기 시간·응답 시간·반환 시간**을 구분해야 합니다.
- 어떤 알고리즘도 모든 상황에서 최고는 아니며 **공정성·응답성·전환 비용** 사이에 균형이 필요합니다.

## Chapter12. 프로세스 동기화
<details>
<summary>핵심 개념 펼치기</summary>

### 1. 왜 동기화가 필요할까?

동시에 실행되는 프로세스·스레드가 **공유 데이터**를 읽고 수정하면 실행 순서에 따라 결과가 달라질 수 있습니다. 이를 **경쟁 상태(Race Condition)**라고 합니다.

**예시: 공유 변수 `count = 0`을 두 스레드가 각각 1 증가**

```text
스레드 A: count를 읽음 → 0
스레드 B: count를 읽음 → 0
스레드 A: 0 + 1 저장 → 1
스레드 B: 0 + 1 저장 → 1
최종 결과: 기대값 2가 아닌 1
```

`count++`처럼 간단해 보이는 문장도 **읽기·계산·쓰기**가 나뉠 수 있습니다. 동기화는 **작업 순서를 조정**하고, 공유 자원을 동시에 수정하지 않도록 보호하는 데 사용합니다.

### 2. 공유 자원과 임계 구역

- **공유 자원:** 여러 실행 흐름이 함께 접근할 수 있는 데이터·장치
- **임계 구역(Critical Section):** 동시에 실행하면 데이터가 꼬일 수 있는 공유 자원 접근 코드
- **상호 배제(Mutual Exclusion):** 한 번에 하나의 실행 흐름만 임계 구역에 진입하도록 보장

임계 구역 문제를 해결하려면 일반적으로 **상호 배제**, **진행(진입 가능한 작업이 불필요하게 멈추지 않음)**, **유한 대기(계속 기다리기만 하지 않음)**를 고려합니다.

### 3. 뮤텍스(Mutex)

**뮤텍스 락**은 임계 구역에 진입하기 전에 **락을 획득**하고, 작업을 마치면 **락을 해제**하는 방식입니다.

```text
lock 획득 → 공유 변수 읽기/수정 → lock 해제
```

이미 다른 실행 흐름이 락을 보유한 경우 기다려야 합니다. 락을 획득한 뒤 해제하지 않으면 다른 작업이 진행하지 못할 수 있습니다.

### 4. 세마포(Semaphore)

세마포는 사용 가능한 자원의 수를 **정수 카운터**로 관리하는 동기화 도구입니다.

- **wait(P):** 자원을 획득할 수 있는지 확인하고 카운터 감소; 불가능하면 대기
- **signal(V):** 자원 사용을 마치고 카운터 증가 또는 대기 중인 작업을 깨움
- **카운팅 세마포:** 예를 들어 연결 가능한 자원이 3개면 최대 3개 작업이 동시에 획득하도록 제한 가능


**뮤텍스와 세마포의 자원 접근 구조**

```text
[1] Mutex : 하나의 임계 구역 보호

        ┌─────────────┐
Thread A│  Lock 획득  │
        └──────┬──────┘
               │
               ▼
        ┌─────────────┐
        │  공유 자원  │
        │    사용     │
        └──────┬──────┘
               │
               ▼
          Lock 해제
               │
               ▼
        Thread B 진입 가능


[2] Semaphore : 여러 자원 사용 수 관리

       사용 가능한 자원 = 2

           ┌───────────┐
           │ count = 2 │
           └─────┬─────┘
                 │
          ┌──────┴──────┐
          ▼             ▼
       Thread A      Thread B
       자원 획득     자원 획득
          │             │
          ▼             ▼
       [자원 1]      [자원 2]

           count = 0
                │
                ▼
             Thread C
                │
                ▼
             대기 상태
                │
         기존 작업이 자원 반환
                │
                ▼
             획득 가능
```

**핵심 차이**

- Mutex : 상호 배제를 위한 잠금
- Semaphore : 사용 가능한 자원 수를 관리
- Semaphore의 wait는 자원 획득,
  signal은 자원 반환 또는 대기 작업 깨우기와 관련된다.


뮤텍스는 주로 **단일 임계 구역 보호**, 세마포는 **여러 개의 동일 자원 수 관리**나 실행 순서 조정에 활용할 수 있습니다.

### 5. 모니터(Monitor)

모니터는 **공유 데이터와 동기화 동작을 하나로 묶어 관리**하는 추상화입니다. 보통 한 번에 하나의 실행 흐름이 모니터 내부의 보호된 구역을 실행하며, **조건 변수(Condition Variable)**를 이용해 특정 조건이 충족될 때까지 대기하거나 다른 작업을 깨울 수 있습니다.

**동기화에서 구분할 것**
- **상호 배제:** 동시에 실행하지 못하게 막기
- **실행 순서 제어:** 어떤 작업이 먼저 완료되어야 다른 작업이 시작되도록 조정

***확인할 개념: 두 스레드가 공유하는 카운터를 각각 10만 번 증가시킨다. synchronized로 임계 구역을 보호한다.***

```java
public class Chapter12Synchronization {
    private static int count = 0;

    private static synchronized void increment() {
        count++; // 읽기 → 더하기 → 쓰기를 하나의 임계 구역으로 보호
    }

    public static void main(String[] args) throws InterruptedException {
        Runnable task = () -> {
            for (int i = 0; i < 100_000; i++) increment();
        };

        Thread a = new Thread(task);
        Thread b = new Thread(task);
        a.start();
        b.start();
        a.join();
        b.join();

        System.out.println("최종 값: " + count); // 200000
    }
}
```

주의: `count++`는 원자적 연산이 아니므로 동기화 없이 실행하면 일부 증가가 소실될 수 있다.

### ✅ Chapter12 핵심 정리

- 동기화는 **공유 자원 접근의 안전성과 실행 순서**를 제어하는 문제입니다.
- `count++`도 동시 실행 시 안전하지 않을 수 있습니다.
- 뮤텍스·세마포·모니터는 목적과 사용 방식이 서로 다릅니다.

</details>

## Chapter13. 교착 상태
<details>
<summary>핵심 개념 펼치기</summary>

### 1. 교착 상태(Deadlock)란?

여러 프로세스가 **서로에게 필요한 자원을 쥔 채 다른 자원을 기다려**, 아무도 다음 단계로 진행하지 못하는 상황입니다.

```text
프로세스 A: 자원 X를 보유하고 Y를 기다림
프로세스 B: 자원 Y를 보유하고 X를 기다림
→ 둘 다 자원을 놓지 않는다면 계속 대기
```

단순히 **처리가 느린 것**과 다릅니다. 서로를 기다리는 관계 때문에 작업을 진행할 수 없다는 점이 핵심입니다. 교재의 **식사하는 철학자 문제**도 이를 설명하는 전형적인 사례입니다.

### 2. 교착 상태의 4가지 필요 조건

| 조건 | 의미 |
|---|---|
| **상호 배제** | 자원을 한 번에 하나의 작업만 사용 가능 |
| **점유와 대기** | 이미 자원을 가진 채 다른 자원 추가 요청 |
| **비선점** | 보유한 자원을 외부에서 강제로 회수할 수 없음 |
| **원형 대기** | A→B→C→A처럼 서로 자원을 기다리는 고리가 형성 |

네 조건이 **모두 성립해야** 전형적인 교착 상태가 발생할 수 있습니다. 하지만 네 조건이 성립하는 환경이라고 해서 언제나 교착 상태가 발생하는 것은 아닙니다.

### 3. 자원 할당 그래프

- **프로세스 → 자원:** 그 자원을 **요청하고 대기**
- **자원 → 프로세스:** 그 자원이 프로세스에 **할당됨**

그래프에 **사이클(고리)**이 있는지 살펴보면 교착 상태를 분석할 수 있습니다. **자원마다 인스턴스가 1개인 경우** 사이클은 교착 상태를 의미하지만, 자원 인스턴스가 여러 개면 사이클만으로 확정할 수 없습니다.


**교착 상태의 원형 대기 구조**

```text
       자원 X
         │
         │ 할당
         ▼
    ┌─────────┐
    │Process A│
    └────┬────┘
         │
         │ 자원 Y 요청
         ▼
       자원 Y
         │
         │ 할당
         ▼
    ┌─────────┐
    │Process B│
    └────┬────┘
         │
         │ 자원 X 요청
         ▼
       자원 X (처음으로 되돌아감)
```

**대기 관계**

```text
Process A
  └─ 자원 X 보유
  └─ 자원 Y 대기

Process B
  └─ 자원 Y 보유
  └─ 자원 X 대기

A → Y → B → X → A

서로 필요한 자원을 기다리므로
두 프로세스 모두 진행할 수 없다.
```

※ 자원 X와 Y가 각각 한 개의 인스턴스만
가진다고 가정한 교착 상태 예시이다.


### 4. 교착 상태 대응 방법

| 방식 | 접근 방법 | 예시 |
|---|---|---|
| **예방** | 4가지 발생 조건 중 하나를 깨도록 설계 | 자원 획득 순서를 전역적으로 통일 |
| **회피** | 요청을 허용해도 안전한 상태가 유지되는지 판단 | 은행원 알고리즘 |
| **검출** | 자원 할당 상태를 조사해 발생 여부 판정 | 대기 관계 검사 |
| **회복** | 이미 발생한 교착 상태 해소 | 프로세스 종료, 자원 회수 등 |

**안전 상태(Safe State)**는 모든 프로세스가 완료될 수 있는 실행 순서가 적어도 하나 존재하는 상태입니다. **불안전 상태(Unsafe State)는 교착 상태와 동일한 뜻이 아니며**, 교착 상태가 발생할 가능성이 있는 상태입니다.

***확인할 개념: 서로 다른 두 스레드가 자원 A, B를 반드시 같은 순서로 획득하도록 한다.***

```java
public class Chapter13LockOrdering {
    private static final Object lockA = new Object();
    private static final Object lockB = new Object();

    private static void work(String name) {
        synchronized (lockA) { // 모든 스레드가 A → B 순서로 잠금
            synchronized (lockB) {
                System.out.println(name + " 작업 완료");
            }
        }
    }

    public static void main(String[] args) throws InterruptedException {
        Thread first = new Thread(() -> work("첫 번째 스레드"));
        Thread second = new Thread(() -> work("두 번째 스레드"));
        first.start();
        second.start();
        first.join();
        second.join();
    }
}
```

주의: 잠금 획득 순서를 통일하면 해당 잠금 간의 원형 대기를 예방할 수 있다.

### ✅ Chapter13 핵심 정리

- 교착 상태는 **원형 자원 대기 때문에 진행이 멈춘 상황**입니다.
- 네 가지 발생 조건을 외우는 것보다 **실제 자원 대기 사례에 적용**할 수 있어야 합니다.
- **예방·회피·검출·회복**은 문제를 다루는 시점과 방법이 다릅니다.

## Chapter14. 가상 메모리
<details>
<summary>핵심 개념 펼치기</summary>

### 1. 연속 메모리 할당과 단편화

프로세스를 **하나의 연속된 물리 메모리 공간**에 배치하면 관리하기는 직관적이지만 빈 공간을 효율적으로 사용하기 어렵습니다.

- **최초 적합(First Fit):** 조건을 만족하는 첫 빈 공간 선택
- **최적 적합(Best Fit):** 들어갈 수 있는 공간 중 가장 작은 공간 선택
- **최악 적합(Worst Fit):** 가장 큰 빈 공간 선택

**외부 단편화:** 빈 공간의 총합은 충분하지만 **연속된 큰 공간이 없어** 할당하지 못하는 문제입니다.

```text
[사용 4][빈 2][사용 3][빈 2][사용 1]
빈 공간 총합 = 4, 하지만 연속된 크기 4 공간은 없음
```

**내부 단편화:** 할당받은 공간 내부에 실제로 사용하지 않는 부분이 남는 문제입니다.

### 2. 스와핑(Swapping)

**스와핑**은 메모리 압박 등에 대응하기 위해 프로세스에 속한 메모리 내용을 저장장치의 스왑 영역으로 내보내거나 다시 가져오는 방식입니다. 저장장치는 RAM보다 느리므로 스왑을 자주 사용하면 실행 속도가 크게 떨어질 수 있습니다. 현대 운영체제에서는 일반적으로 전체 프로세스가 아니라 **페이지 단위의 이동** 등 더 세분화된 방식을 활용합니다.

### 3. 가상 메모리와 페이징(Paging)

운영체제와 하드웨어는 프로그램에 **연속된 것처럼 보이는 가상 주소 공간**을 제공하고, 실제 물리 메모리는 여러 위치에 나누어 배치할 수 있습니다.

- **페이지(Page):** 가상 주소 공간을 일정한 크기로 나눈 단위
- **프레임(Frame):** 물리 메모리를 같은 크기로 나눈 단위
- **페이지 테이블(Page Table):** 가상 페이지가 어느 물리 프레임에 대응하는지 등의 정보 관리
- **PTE(Page Table Entry):** 한 페이지의 대응 프레임, 유효성, 권한 등 기록

```text
가상 주소 = [페이지 번호 | 페이지 내부 오프셋]
                         ↓ 페이지 번호로 페이지 테이블 조회
물리 주소 = [프레임 번호 | 같은 오프셋]
```

**간단한 계산:** 페이지 크기가 1 KiB(1,024바이트)일 때 가상 주소 **2500**은 `페이지 번호 2, 오프셋 452`입니다. 페이지 테이블이 2번 페이지를 물리 프레임 7에 연결한다면, 물리 주소는 `7×1024+452 = 7620`이 됩니다.

### 4. TLB와 주소 변환 속도

주소를 읽을 때마다 페이지 테이블을 메모리에서 직접 찾으면 부담이 있습니다. **TLB(Translation Lookaside Buffer)**는 최근 사용한 가상→물리 주소 변환 정보를 빠르게 보관하는 캐시입니다.

**가상 주소 변환과 페이지 폴트 처리**

```text
      CPU가 가상 주소에 접근
                │
                ▼
         ┌────────────┐
         │  TLB 조회  │
         └──────┬─────┘
                │
        ┌───────┴────────┐
        │                │
      적중              미스
        │                │
        ▼                ▼
  프레임 번호 확인    페이지 테이블 조회
        │                │
        │        ┌───────┴────────┐
        │        │                │
        │    페이지 존재       페이지 부재
        │        │                │
        │        ▼                ▼
        │    TLB 갱신       페이지 폴트
        │        │                │
        │        │                ▼
        │        │        운영체제가 페이지 적재
        │        │                │
        │        │                ▼
        │        │        페이지 테이블 갱신
        │        │                │
        │        └────────┬───────┘
        │                 │
        └────────┬────────┘
                 ▼
           물리 메모리 접근
```

**핵심 차이**

- TLB 미스 : 주소 변환 정보가 TLB에 없는 상태
- 페이지 폴트 : 페이지 접근을 처리하기 위해
  운영체제의 개입이 필요한 상태
- TLB 미스가 발생해도 페이지가 RAM에
  존재한다면 디스크에서 가져올 필요는 없다.

※ 정상적인 요구 페이징 상황을 단순화한 그림이다.
잘못된 주소나 접근 권한 위반은 오류 처리될 수 있다.


- **TLB 적중:** 필요한 변환 정보가 있어 빠르게 접근
- **TLB 미스:** 페이지 테이블 등을 참조하여 변환 정보 확인

**TLB 미스는 페이지 폴트와 다릅니다.** TLB에 변환 결과가 없어도 해당 페이지가 물리 메모리에는 존재할 수 있습니다.

### 5. 요구 페이징과 페이지 폴트

**요구 페이징(Demand Paging)**은 필요해진 페이지를 그때 물리 메모리에 가져오는 방식입니다.

```text
① 프로그램이 특정 가상 주소에 접근
② 필요한 페이지가 RAM에 없어 페이지 폴트 발생
③ 운영체제가 해당 페이지를 저장장치 등에서 확보
④ 빈 프레임을 찾거나 기존 페이지를 교체
⑤ 페이지 테이블 갱신 후 명령어 실행 재개
```

페이지 폴트가 항상 저장장치 읽기를 요구하는 것은 아니며, 잘못된 주소나 권한 위반으로 발생하면 정상적인 적재 대신 오류 처리로 이어질 수 있습니다. **정상적인 요구 페이징 사례**에서는 위와 같이 처리합니다.

### 6. 페이지 교체 알고리즘과 스래싱

RAM에 빈 프레임이 없을 때 어느 페이지를 내보낼지 선택해야 합니다.

| 알고리즘 | 교체 대상 | 특징 |
|---|---|---|
| **FIFO** | 가장 먼저 적재된 페이지 | 단순하지만 비효율적 상황 가능 |
| **OPT** | 앞으로 가장 오랫동안 사용하지 않을 페이지 | 미래 정보가 필요하므로 이론적 기준 |
| **LRU** | 가장 오랫동안 사용하지 않은 페이지 | 최근 사용 기록을 근거로 판단 |

**스래싱(Thrashing)**은 메모리가 부족하거나 작업 집합에 비해 프레임 할당이 적어 **페이지 교체만 지나치게 반복**되고 실제 작업 성능이 크게 떨어지는 현상입니다. 프레임 배분과 동시에 실행하는 작업 수를 적절히 조절하는 것이 중요합니다.

***확인할 개념: 페이지 크기 1024바이트, 페이지 테이블을 가정하고 페이지 번호와 오프셋으로 주소를 변환한다.***

```java
public class Chapter14Paging {
    private static final int PAGE_SIZE = 1024;
    // 페이지 번호 0,1,2에 해당하는 프레임 번호. -1은 현재 미적재.
    private static final int[] pageTable = {3, -1, 7};

    private static void translate(int virtualAddress) {
        int page = virtualAddress / PAGE_SIZE;
        int offset = virtualAddress % PAGE_SIZE;
        if (virtualAddress < 0 || page >= pageTable.length) {
            throw new IllegalArgumentException("가상 주소 범위 초과");
        }
        if (pageTable[page] == -1) {
            System.out.println("페이지 폴트: " + page + "번 페이지 미적재");
            return;
        }
        int physicalAddress = pageTable[page] * PAGE_SIZE + offset;
        System.out.println("가상 주소 " + virtualAddress + " → 물리 주소 " + physicalAddress);
    }

    public static void main(String[] args) {
        translate(2500); // 페이지 2, 오프셋 452 → 프레임 7 → 7620
        translate(1500); // 페이지 1이 메모리에 없어서 페이지 폴트
    }
}
```

주의: 페이지가 메모리에 없는 경우의 표시만 구현한 페이징 시뮬레이션이다. 실제 OS의 적재 과정은 포함하지 않는다.

### ✅ Chapter14 핵심 정리

- 가상 메모리는 **가상 주소와 물리 주소를 분리하여 메모리를 효율적으로 사용·보호**합니다.
- **페이지·프레임·페이지 테이블·TLB**의 역할을 분명히 구분해야 합니다.
- 페이지 폴트와 교체는 정상적인 메모리 관리의 일부이지만 너무 잦으면 성능이 떨어집니다.

</details>

## Chapter15. 파일 시스템
<details>
<summary>핵심 개념 펼치기</summary>

### 1. 파일과 디렉터리

**파일(File)**은 저장장치의 데이터를 프로그램이 이름으로 접근할 수 있게 하는 논리적 단위입니다. 파일 시스템은 파일의 실제 블록 위치와 속성을 관리합니다.

- **파일 메타데이터:** 크기, 생성·수정 시각, 권한, 저장 위치 관련 정보 등
- **디렉터리(Directory):** 파일·하위 디렉터리를 이름으로 찾아갈 수 있게 관리
- **경로(Path):** 파일을 찾기 위한 위치 표현

| 경로 | 의미 | 예시 |
|---|---|---|
| 절대 경로 | 루트에서 시작하는 경로 | `/home/user/note.txt` |
| 상대 경로 | 현재 작업 디렉터리를 기준으로 하는 경로 | `docs/note.txt` |

`.`은 **현재 디렉터리**, `..`은 **부모 디렉터리**를 뜻합니다(유닉스 계열 경로 예시).

### 2. 파티셔닝과 포매팅

- **파티셔닝(Partitioning):** 저장장치의 공간을 논리적 영역으로 나눔
- **포매팅(Formatting):** 해당 영역에 파일 시스템의 구조를 생성하여 파일을 저장할 준비를 함

파티션을 나누는 것과 파일 시스템을 만드는 것은 **서로 다른 작업**입니다.

### 3. 파일 할당 방식

| 할당 방식 | 저장 방법 | 장점·한계 |
|---|---|---|
| **연속 할당** | 파일의 블록을 연속해서 배치 | 순차·임의 접근이 단순하지만 외부 단편화 문제 |
| **연결 할당** | 블록이 다음 블록을 가리키도록 연결 | 빈 공간 활용은 유리하지만 임의 접근이 비효율적일 수 있음 |
| **색인 할당** | 별도 색인 블록에 데이터 블록의 위치 기록 | 흩어진 블록도 탐색하기 편하지만 색인 관리 필요 |


**연속·연결·색인 할당의 저장 구조**

```text
[1] 연속 할당

디스크 블록
┌────┬────┬────┬────┬────┬────┐
│ B0 │ B1 │ B2 │ B3 │ B4 │ B5 │
├────┼────┼────┼────┼────┼────┤
│기타│ A1 │ A2 │ A3 │빈칸│기타│
└────┴────┴────┴────┴────┴────┘
       └──── 파일 A ────┘

→ 하나의 파일을 연속된 블록에 저장


[2] 연결 할당

파일 A의 블록 연결

┌────┐       ┌────┐       ┌────┐
│ B1 │ ────→ │ B5 │ ────→ │ B3 │
└────┘       └────┘       └────┘
                               │
                               ▼
                              끝

→ 파일 블록이 떨어져 있어도 연결 가능
→ 다음 블록의 위치 정보를 이용


[3] 색인 할당

         ┌───────────┐
         │ 색인 블록 │
         ├───────────┤
         │ B2        │────→ [데이터 1]
         │ B7        │────→ [데이터 2]
         │ B4        │────→ [데이터 3]
         └───────────┘

→ 색인 블록이 데이터 블록의 위치를 관리
→ 데이터 블록이 연속될 필요 없음
```


### 4. FAT와 유닉스 파일 시스템

**FAT(File Allocation Table)**
- 파일을 이루는 블록(클러스터)의 **다음 위치 정보**를 FAT에서 관리
- 디렉터리에는 파일 이름과 첫 클러스터 등 관련 정보가 기록됨
- 파일을 읽을 때 테이블의 연결 관계를 따라 데이터에 접근할 수 있음

**유닉스 계열의 inode 방식**
- **inode:** 파일의 소유자·권한·크기·데이터 블록 위치 등의 메타데이터 관리
- **디렉터리 엔트리:** 파일 이름과 inode 식별자를 연결
- 파일 이름과 파일 데이터는 **서로 다른 관리 정보**로 연결됨

**중요한 차이:** FAT는 **클러스터 연결 정보가 테이블에 중심적으로 저장**되고, inode 방식은 **각 파일의 메타데이터·블록 위치를 inode가 관리**합니다.

### 5. 저널링과 마운트

- **저널링(Journaling):** 파일 시스템의 변경 과정을 기록하여 예기치 않은 장애 이후 일관성 복구를 돕는 기법입니다. 모든 사용자 데이터가 항상 복구된다는 보장은 아닙니다.
- **마운트(Mount):** 별도 파일 시스템을 운영체제의 디렉터리 트리의 특정 위치에 연결하여 사용할 수 있게 하는 작업입니다.

**예시:** USB 메모리에 저장된 파일을 열 수 있는 것은 운영체제가 해당 장치의 파일 시스템을 인식하고 접근 경로를 제공하기 때문입니다.

***확인할 개념: 운영체제가 제공하는 파일 API를 통해 파일을 생성하고 쓰고 읽고 삭제한다.***

```java
import java.nio.charset.StandardCharsets;
import java.nio.file.Files;
import java.nio.file.Path;

public class Chapter15FileSystem {
    public static void main(String[] args) throws Exception {
        Path file = Files.createTempFile("cs-study-", ".txt");
        try {
            Files.writeString(file, "컴퓨터 구조와 운영체제", StandardCharsets.UTF_8);
            System.out.println("파일: " + file.getFileName());
            System.out.println("내용: " + Files.readString(file, StandardCharsets.UTF_8));
            System.out.println("크기(byte): " + Files.size(file));
        } finally {
            Files.deleteIfExists(file); // 실습용 임시 파일 정리
        }
    }
}
```

주의: Java의 파일 API는 파일 내용과 경로를 다루며, FAT·inode의 실제 디스크 블록 배치를 직접 보여 주지는 않는다.

### ✅ Chapter15 핵심 정리

- 파일은 논리적인 데이터 단위이고, 파일 시스템은 **이름·속성·물리적 저장 블록의 대응 관계**를 관리합니다.
- **연속·연결·색인 할당**, **FAT·inode 방식**의 차이를 이해해야 합니다.
- 저널링은 장애 복구를 지원하고, 마운트는 파일 시스템을 디렉터리 트리에 연결합니다.
